# tart-catalogue-core

TLE propagation and coordinate transforms for the TART catalogue: pure
computation, no I/O. Given TLE records as served by `/ephemerides`, it
propagates them with [sgp4](https://crates.io/crates/sgp4) and converts the
result to ECEF, or to azimuth/elevation/range for an observer.

```
time.rs          unix -> Julian Date, GMST, TEME -> ECEF rotation
geo.rs           geodetic -> ECEF, Z-rotation, ECEF -> ENU horizontal
propagation.rs   TLE -> SGP4 propagator, TEME/ECEF states, horizontal
                 positions, bulk (many instants x many satellites)
```

Deliberately absent, because they are client concerns: the network fetch, the
TLE cache, and any wasm bindings. Nothing here depends on tokio, reqwest or
the filesystem, so the crate builds for `wasm32-unknown-unknown` — the TART
viewer links it from a thin wasm wrapper of its own.

The bulk entry point exists because a viewer scrubbing a visibility history
asks for positions at up to 3600 instants across every satellite; the
TEME->ECEF rotation is computed once per instant and shared across
satellites, which is what makes that interactive.

Correctness is gated by parity against the astropy-generated vectors in
`tests/` (vendored from `../test-vectors/`, regenerated by
`test-vectors/generate.py`); they are why the epoch-unit bug of issue #9
cannot come back silently.

## Consumers

- `tart-catalog-client-rs` — the CLI client in this repo, built on the core.
- the TART web app's wasm wrapper — `tart-catalogue-wasm` in
  [tart-telescope/web_app](https://github.com/tart-telescope/web_app), which
  is expected to thin down to the bindings plus this crate.
